# Architectural decisions

## D-001 Avalonia 12 for the desktop UI

**Decision.** Avalonia 12.1.4 (MIT) with the Fluent dark theme. **Why.** Cross-platform desktop on .NET 10, mature, actively maintained, with a retained control tree for panels and an immediate-mode `DrawingContext` for custom surfaces. **Alternatives.** WPF/WinUI (Windows-only); MAUI (weak desktop tooling); a game-engine renderer (unjustified dependency).

## D-002 Custom canvas on Avalonia's DrawingContext

**Decision.** The node canvas is one `Control` that draws nodes, pins, and wires itself, with view-only layout objects, cached text, viewport culling, and no per-node controls. **Why.** Thousands of nodes as individual controls would make layout and hit-testing the bottleneck; a single drawing surface keeps the cost proportional to what is visible. A separate GPU layer is not justified until measurements show the DrawingContext path is the bottleneck (see PERFORMANCE.md).

## D-003 Roslyn for emission and verification

**Decision.** Microsoft.CodeAnalysis.CSharp 5.0.0 (MIT): `SyntaxFactory` to build code, `NormalizeWhitespace` to format, in-memory `CSharpCompilation` to verify. **Why.** Structurally correct output by construction, deterministic formatting, and real C# diagnostics before writing files. The Workspaces formatter was not used: it adds MEF and workspace dependencies for little benefit at this stage.

## D-004 Few assemblies

**Decision.** Six source projects instead of the fifteen originally sketched. Type system, diagnostics, node library, IR, and emission are folders in the compiler; serialization is in the graph model; build integration is in the project system. **Why.** Each split should serve a real consumer. The node-library SDK became the seventh project when external libraries were supported (D-038).

## D-005 IR between graph and syntax

**Decision.** Node definitions lower to a small IR (`IrExpression`, `IrStatement`); only the emitter knows Roslyn. **Why.** Keeps node authoring independent of Roslyn, allows simplification passes, and lets new targets or formatting change without touching nodes.

## D-006 Structured control flow from post-dominators

**Decision.** Execution graphs are structured into nested blocks using immediate post-dominators; unstructured shapes are rejected (VSG0017) rather than compiled with `goto` or a state machine. **Why.** The product promise is readable C#. Rejecting rare unstructured graphs with a clear message is better than emitting code nobody would write.

## D-007 Pure nodes are inlined

**Decision.** Side-effect-free nodes are inlined at each use; statement-node outputs become locals. **Why.** Produces the most natural code for typical graphs (`"Hello, " + line + "!"`). Shared-subexpression hoisting is a planned optimization.

## D-008 Ownership by file header

**Decision.** Generated files live in `Generated/` and carry a fixed header; the writer only overwrites or deletes files that carry it. The `.csproj` is created once and then belongs to the user. **Why.** Never silently destroy handwritten work, while keeping the project buildable with plain `dotnet build`.

## D-009 Project file extension `.vside`

**Decision.** Not `.vgproj`. **Why.** MSBuild treats any `*.*proj` in a folder as a project, which made `dotnet build` in a generated project folder fail with MSB1011. Found by building a sample with the plain CLI.

## D-010 AvaloniaEdit for code views

**Decision.** Avalonia.AvaloniaEdit 12.0.0 (MIT) for the generated-code and output views, with the built-in C# definition recolored for the dark theme. **Why.** A real editor component with line numbers, selection, search, and efficient appends; TextMate grammars can replace the built-in definition later.

## D-011 Comments are the grouping mechanism

**Decision.** A comment is a titled box stored in the graph (`comments`, schema version 2). Dragging its title moves every node and comment lying completely inside it. Membership is derived from geometry at drag time and never stored. **Why.** One concept covers both documentation and grouping, as in Unreal Blueprints; storing membership would need bookkeeping whenever a node moves in or out. Comments are ignored by the compiler, so they cannot change generated code.

## D-012 Reroute points are wire layout, not nodes

**Decision.** A reroute point is a position stored on the connection (`points`, schema version 3). Connection equality ignores points. **Why.** Points never affect meaning, so the compiler, connection rules, and diagnostics stay untouched. Reroute nodes, as in Unreal Blueprints, would need pass-through pins whose type depends on what is connected, which the type system does not have. Trade-off: one knot cannot fan out to several inputs; each wire is rerouted separately.

## D-013 xUnit v3

**Decision.** xunit.v3 3.2.2 with Microsoft.NET.Test.Sdk. Integration tests launch the real `dotnet` CLI instead of mocking the build.

## D-014 The command palette is built from the menu

**Decision.** The command palette lists the main menu's enabled leaf items (plus one "Add Node" entry per node) and runs them by raising the item's `Click`. **Why.** The menu stays the single list of commands, so a command added to the menu appears in the palette with its shortcut and enabled state, and there is no second registry to keep in sync. Trade-off: a command must have a menu item to be searchable. The same overlay lists the connections between two selected nodes for keyboard connecting (Ctrl+L); the list comes from `GraphEditor.PossibleConnections`, which applies the same rules as dragging a wire.

## D-015 Variables are declared on the graph; their nodes are resolved per node

**Decision.** A graph lists its variables (`variables`, schema version 4). Get and Set nodes store only the variable's id, and `NodeLibrary.Resolve` builds their definition from the variable. **Why.** A node's pins must follow the variable's current name and type; storing pins in the file, or registering one node type per variable, would let them drift apart when a variable is renamed or retyped. Referring by id keeps renames free. Changing a type removes the wires that no longer fit, in the same undo step. The same per-node resolution is what function call nodes need. Trade-off: copying a variable node into a graph that lacks the variable leaves a node that reports VSG0021 until it is deleted.

## D-016 Loops are nodes with a body output, not backward wires

**Decision.** Repetition uses While Loop and For Loop nodes. Their Loop Body output starts a nested region; the iteration ends where that flow ends. Wires pointing back to an earlier node stay an error. **Why.** Backward wires allow arbitrary gotos that have no structured C# form, and recovering loops from them would make the generated code depend on graph shape heuristics. A body region maps one-to-one onto a C# block, keeps the existing post-dominator lowering unchanged, and gives locals declared in the body the same scope they have in C#. Trade-off: a loop whose exit is in the middle of the body needs a Branch and a Break node.

## D-017 Functions are separate graphs in one partial class

**Decision.** A function is its own graph file (`kind: Function`, schema version 5) with parameters and an optional return type. It generates a `private static` method (`public static` since D-025) in its own `.g.cs` file, as part of `partial class Program`. Call nodes store only the function's graph id and are resolved per node, like variable nodes. A call is always a statement node with execution pins. **Why.** One graph per method keeps each canvas readable and maps one-to-one onto generated files and source maps. A partial class lets each graph compile to its own file without a merge step. Resolving by id keeps calls intact when a function or parameter is renamed. Calls run in execution order because a function may have side effects; a pure call node would be inlined at every use and run more than once. A function with a return type must end every path at Return Value (VSG0026), so the generated method always compiles. Trade-off: removing a parameter leaves wires on call nodes in other graphs, which the compiler reports until they are deleted.

## D-018 Shared pure values are hoisted per statement

**Decision.** When one statement uses a pure node with inputs more than once, the value is computed once into a local declared just before that statement. Values shared between statements, and loop inputs (While condition, For end), stay inline. **Why.** Within one statement nothing runs between the uses, so one evaluation is equivalent and the code reads like hand-written C#. Between statements a Set node may change a variable the value reads, and a loop condition must be evaluated on every iteration; hoisting there would change behavior. Literals and variable reads stay inline because a local would add nothing. Trade-off: a value shared by two statements is still computed twice.

## D-019 Exceptions use one Try node with nested blocks

**Decision.** A Try node has Try, Catch, and Finally outputs that start nested blocks, like a loop body, and a Completed output. Catch handles every `Exception` and offers its Message as a string output. Throw Error throws `InvalidOperationException` with a message. **Why.** Nested blocks map one-to-one onto `try`/`catch`/`finally` and reuse the region lowering that loops already have (`PinDefinition.Block`). Exception types other than `Exception` and `string` messages would need the type system to know exception classes, which waits for external .NET types. Jumps out of Finally are reported as VSG0028 instead of being left to Roslyn (CS0157), so the error points at the node. Trade-off: no typed catch clauses, no rethrow, and no exception filters yet.

## D-020 Lists are the one generic type; list nodes are registered per element type

**Decision.** `TypeRef` has an optional `ElementType`, used for `List<T>` of `bool`, `int`, `double`, or `string`. Variables, parameters, and return values can be lists; their type is stored by C# name (`List<int>`), so the file format needs no new fields. List nodes (`list.int.add`, `flow.foreach.string`, …) are registered once per element type. Create List is a statement node. **Why.** One element type parameter covers the collections programs need first, and keeps `TypeRef` a record with value equality. Pins have fixed types, and generic pins resolved from connections would touch the editor, the connection rules, and the compiler at once; per-type registration follows the existing arithmetic nodes. Creating a list must happen once per run, but pure nodes are inlined at every use, so creation is a statement. An older build reports a list variable as an unsupported type instead of misreading it, so the schema version is unchanged. Trade-off: four copies of each list node in the palette, and no nested lists or dictionaries yet.

## D-021 .NET methods are discovered with Roslyn and named by documentation ID

**Decision.** `ExternalApi` loads assemblies as Roslyn metadata references and offers each public, ordinary, non-generic, non-obsolete method of a public top-level type whose parameters (no ref, out, in, or params) and return type map to graph types. Instance methods are offered only on types graphs have values of (`string`). The node type ID is `dotnet:` plus the documentation comment ID, for example `dotnet:M:System.Math.Max(System.Int32,System.Int32)`. Framework methods are limited to an allow-list of types (`Math`, `String`, `Convert`, `Environment`, `File`, `Path`, `Thread`); a project's `<Reference HintPath>` assemblies and restored NuGet compile assets (`obj/project.assets.json`) contribute every public type. Methods of `Math` and `String` are pure; all others are statement nodes. A nullable string or list result is coalesced to an empty value. **Why.** Roslyn is already a dependency and sees exactly what the C# compiler will bind, including nullable annotations; reflection would load code into the IDE. Documentation IDs are stable, unique per overload, and readable in the file. Treating unknown methods as statements keeps side effects in execution order. The allow-list keeps the palette usable; the whole framework is thousands of methods. A graph whose package is missing keeps its nodes and reports VSG0001, as for any unknown node type. Trade-off: no constructors, properties, events, or generic methods yet; packages are known only after restore, which the CLI runs when needed and the IDE runs with every build.

## D-055 The Windows installer is a Velopack Setup.exe with the package id ScriptArt.Code

**Decision.** `eng/package.ps1` runs `vpk pack` (when the Velopack tool is installed) on the published win-x64 folder and produces `ScriptArt.Code-win-Setup.exe`, a portable zip, and the update packages and feed files (`releases.win.json`, `RELEASES`) that are uploaded to GitHub Releases. `Program.Main` calls `VelopackApp.Build().Run()` first, so the installer's hooks run before any UI. The package id is `ScriptArt.Code`, not `ScriptArtCode`. **Why.** Velopack installs per user into `%LocalAppData%/<package id>` and removes that folder on uninstall; `%LocalAppData%/ScriptArtCode` already holds recovery copies (D-045) and netcoredbg, which an uninstall must keep. The package id is part of the update channel and must not change once released. Trade-off: the install folder and the data folder have different names. Not done yet: the update check in the IDE, the `.vside` file association, and Linux and macOS installers (vpk packs only for the OS it runs on).

## D-054 The IDE is graph-first; files are for reference

**Decision.** The left panel opens on **My Project** (graphs, types, variables), then the Palette, then **Files** (the former Explorer, D-043). Files' new button offers Function, Class, and Struct graphs before a C# file and any other file. A file named `.vside` or `.graph.json` cannot be created as a plain file (`ProjectFiles.CreateFile`): visual scripts are graphs added to the project. Double-clicking the project file shows My Project; its JSON opens only through **Open as Text**. Continue and the step buttons appear in the toolbar only while debugging. **Why.** ScriptArt Code is visual scripting software; the file tree and text editor exist for reference and handwritten code. A user who made `testing.vside` with New File expected a visual script and got an empty JSON editor. Trade-off: reaching a text file takes one more click than in D-043.

## D-053 The Godot game is debugged by attaching; the language server is deferred

**Decision.** F5 with debugging on a Godot project builds it, starts the game with the Godot executable from preferences, waits until the process has loaded CoreCLR, and attaches netcoredbg to it (`DebugSession.StartGodotAsync`), with the same breakpoints, stepping, call stack, and locals as for console programs. The startup hook that holds a console program before `Main` is not used: Godot hosts the runtime itself. The Godot 4 C# language server (roadmap Phase 7) is not built in this phase. **Why.** Attaching needs nothing from Godot beyond its process; netcoredbg already speaks the protocol the IDE uses. The IDE's own verification already gives completion-free but exact diagnostics on nodes, with Godot's generators (D-050); a language server adds completion, hover, and navigation in handwritten C#, which is a separate editor feature with its own shipping question (which server, how it is installed). Trade-off: code that runs before the debugger has attached, usually the first scene's `_Ready`, does not stop at breakpoints; the Output panel says so. Debugging the game has not been checked with netcoredbg on this machine.

## D-052 Cast To tests a value's class and names it inside a block

**Decision.** A Cast To node (`type.cast`, property `castType` with the class's name, palette category Casting) takes any `object` and has two blocks: Succeeded, where the value is available as the class, and Failed. It generates `if (value is InputEventKey inputEventKey) { … } else { … }` (`IrTypeTest`, `NestedBlock.Conditional`); the cast value used outside Succeeded is VSG0013. It is offered for every non-generic class of the project and every .NET class, and accepts any class name typed in its property; `string`, lists, dictionaries, and value types are errors. Every class value connects to an `object` input. A parameter of an overridden method named with a C# keyword (Godot's `_Input(InputEvent @event)`) is renamed `theEvent` in the graph. **Why.** Godot passes input as the base class `InputEvent`; scripts tell keys, mouse buttons, and actions apart by testing the class. A pattern with a declaration keeps the value typed only where the test succeeded, which a separate cast node with a nullable result could not. Trade-off: no casts to value types or interfaces.

## D-051 Godot signals: built-in ones are .NET events, a class's own are [Signal] delegates

**Decision.** .NET discovery offers public events whose delegate returns `void` and whose parameters map to graph types as On nodes (`dotnet:` plus the event's documentation ID, `E:Godot.BaseButton.Pressed`), named `On BaseButton.Pressed`. Their Handler block runs each time the event happens; the event's values are outputs inside it only. They generate `button.Pressed += () => { … };` with an implicitly typed lambda, so `float` and `StringName` parameters keep their .NET types. A class deriving from a Godot class declares its own signals in Details (`signals` in graph schema 9: a name and values written like `int damage, string source`); each generates `[Signal] public delegate void HitEventHandler(int damage);`. Emit (`signal.emit`) generates `EmitSignal("Hit", damage)` and On (`signal.on`) generates `Connect("Hit", Callable.From((int damage) => { … }))`; both store the class graph's id and the signal's id like property nodes, and their value pins are named by the values' ids, which survive editing the list. Inside a handler, Break, Continue, and Rethrow cannot reach the method's loops and catch blocks (`NestedBlock.Handler`). Signal values can be `bool`, `int`, `double`, `string`, and .NET types; only a class deriving from a Godot class can declare signals. **Why.** GodotSharp exposes every built-in signal as a C# event, so .NET discovery covers them without Godot-specific code. A class's own signals need Godot's source generator, which writes the event and `SignalName`; naming the signal with a string and connecting through `Callable` compiles without the generator, so the code builds before it has run. Verified in Godot 4.8: a class's handler receives the value it emits. Trade-off: handlers cannot be disconnected; a signal can only be emitted on a value of the class that declares it.

## D-050 Approved source generators run when the IDE checks code

**Decision.** The IDE runs the source generators of a project's restored packages (files under `analyzers/dotnet/cs/` in `project.assets.json`, such as `Godot.SourceGenerators`) when it verifies generated and handwritten code, but only those the user approved. Approval is per file and SHA-256 hash, stored in `preferences.json` (`approvedSourceGenerators`); the assembly is read once, its hash checked, and loaded from those bytes, so a file changed after approval does not run. After a restore the IDE asks once per session (Project → Approve Source Generators… asks again). A generator that cannot be loaded is warning VSG0032 and verification continues without it. For a Godot project the generators get the build properties `GodotProjectDir`, `GodotSourceGenerators`, and `IsGodotToolsProject` that Godot.NET.Sdk sets. **Why.** Godot's generators write `PropertyName`, `SignalName`, and the signal events; handwritten code that uses them reported false errors. A generator is code from a package, and opening a project must never run code (AGENTS.md, D-038), so it is trusted like a node library. Hashing the bytes that are loaded closes the gap between checking and loading. Trade-off: a generator loaded into the IDE stays loaded until it exits; an updated package asks again.

## D-049 Operators of .NET types are nodes written as operators

**Decision.** .NET discovery offers a type's arithmetic, comparison, and negation operators (`op_Addition`, `op_Subtraction`, `op_Multiply`, `op_Division`, `op_Modulus`, `op_Equality`, `op_Inequality`, the four orderings, and `op_UnaryNegation`) as pure nodes, named like `Vector2 + Vector2`, with the documentation ID as type ID like other members. They lower to the IR's binary and unary expressions, so the code reads `a + b * (float)delta`, not `Vector2.op_Addition(…)`, which C# rejects. Conversions, `true`/`false`, increment, and bitwise operators are not offered. Generic methods are also offered when a type parameter is constrained to classes (`where T : class`, Godot's `GetNode<T>`); the node library accepts only classes as their type arguments: `string`, lists, dictionaries, classes of the project, and .NET classes. **Why.** Godot's vector math is written with operators; without them, moving a character needs one node per component. Trade-off: an operator with a `float` operand shows the operand as `double` (D-048), so `Vector2 * double` is offered, not `Vector2 * float`.

## D-048 Godot's float and StringName are double and string to graphs

**Decision.** .NET discovery reads a `float` result, property, or field as a `double`, and passes a `double` to a `float` parameter with a `(float)` cast. A type with public implicit conversions both to and from `string` (Godot's `StringName` and `NodePath`) is a `string` for its parameters and results; C# converts it at the call. When a `float` overload has the same graph types as a `double` one, only the `double` one is offered, so existing node type IDs stay. Methods with `float` in their signature cannot be overridden, since the override would have to declare `float`. Public fields are offered like properties (Godot's `Vector2.X`); a field of a struct is read-only, as for struct properties. **Why.** Godot's API uses `float` for nearly every number and `StringName` for every action and property name; without these mappings most of it is hidden. A separate `float` graph type would double the math nodes and add conversions users must place by hand, for precision games do not need. Trade-off: arguments are narrowed silently; a `double` too large for a `float` becomes infinity.

## D-047 Godot scripts are class graphs with a .NET base class

**Decision.** A class graph has an optional `baseType` (graph schema 9), the full name of a .NET class offered by the project's references that is not sealed and has a parameterless constructor; structs and generic classes cannot have one. It generates `public partial class Name : Base` in `Generated/Name.cs` (not `.g.cs`), because Godot's source generator gives a `[ScriptPath]` only to the class in the file named after it, and a scene finds its script by that path. Every part of the class repeats `public partial` and the base; its properties and methods are `internal`, so they may use the project's internal types; a parameterless constructor stays public so Godot can create the object. A method named and typed like a public virtual method of a base class (`_Ready()`, `_Process(double)`, `_PhysicsProcess(double)`) is generated as `public override`; one that returns something else is an error. A value of a class connects to inputs of each class it derives from (`NodeLibrary.BaseTypesOf`, passed to the connection rules by the editor and the compiler). A project whose `.csproj` uses `Godot.NET.Sdk` is a Godot project: it is verified as a library (no `Main`), its restore output is read from `.godot/mono/temp/obj`, and it always needs a restore for GodotSharp. File → New Godot Project writes a `Godot.NET.Sdk/4.4.1` project with `project.godot` and `Main.tscn` (kept when present) and a `Main : Godot.Node` whose `_Ready` prints a greeting. Details → Base class and **Override Method** set the base and add overrides with the right parameters. A property of such a class can be exported (`export`, graph schema 9): it is generated with Godot's `[Export]`, so the Godot editor shows and saves it per node; only `bool`, `int`, `double`, `string`, and .NET types can be exported, and only by a class that derives from `Godot.GodotObject`. Run (F5) builds a Godot project and starts it with the Godot 4 .NET executable chosen in Tools → Preferences (`godotPath`), as `godot --path <project folder>`, and shows its output; Stop ends the game. **Why.** Godot scripts are ordinary C# classes; reusing class graphs, methods, and .NET discovery adds Godot without Godot-specific node types. Verified against the real Godot.NET.Sdk 4.4.1 in an integration test that restores, generates, builds, and finds the generated `ScriptPath`, and by a test that runs the sample in Godot when `SCRIPTART_GODOT` names the executable (checked with Godot 4.8). Godot 4.4 is the minimum: the oldest release whose SDK targets .NET 8; the Godot editor raises the SDK version when it opens a project. Trade-off: until restore the Godot API is unknown, so a new Godot project shows errors until its packages are restored; Godot's own source generators run during verification only once approved (D-050).

## D-046 Dark and light themes from one set of tokens, checked for contrast

**Decision.** `Theme.axaml` defines every IDE color as a token in a Dark and a Light theme dictionary, used through dynamic resources; code reads them through the window's theme variant. `CanvasTheme` has a dark and a light palette behind the same members and is switched, with syntax and diff colors (`IdeColors`), when the window's theme changes. Node headers keep their category colors with light titles in both themes. Icon colors are mid-tones with 3:1 contrast on the panels of both themes. Preferences offer Dark, Light, and System (follows the operating system). `ThemeContrastTests` checks WCAG AA: 4.5:1 for text on each background it is drawn on, 3:1 for pins, wires, outlines, and icons. **Why.** One set of names keeps XAML and code unchanged when a theme is added, and a test keeps new colors honest. The review found two failures in the dark theme, now fixed: pin type labels (3.87:1) and white text on selected rows in My Project (3.20:1; selection now has its own token). Trade-off: colors chosen in code (the canvas) are not visible to designers in XAML.

## D-045 Autosave keeps recovery copies outside the project

**Decision.** Every autosave interval (Preferences, default 60 s, 0 = off) the IDE writes what saving would write, for files that differ from disk (the project file, graphs, and open text files), to `%LocalAppData%/ScriptArtCode/recovery/<hash of the project file path>/` with a `manifest.json` (schema 1: project path, time, relative file paths) and the files as they were on disk under `base/`. Autosave never writes the project's own files and refuses paths outside the project and generated text. Saving, or closing with Don't Save, removes the copies. When a project opens with copies newer than its files, the generation diff view shows how restoring would change each file; **Restore** writes them and reopens the project, **Discard** deletes them. A manifest that names another project or a path outside the project is ignored. **Why.** Writing over the user's files unasked would make autosave a second save with no undo; copies elsewhere cost nothing when the IDE exits normally and lose at most one interval when it is killed. Reusing the diff view shows exactly what restoring changes. A file saved after the copy (in the IDE or another tool) is merged line by line with the recovered work, against the file as it was when the copy was made (kept under `base/`); when both changed the same or adjacent lines, or a merged graph or project file no longer reads, the saved file wins and the copy is not offered. Trade-off: a line merge, not a graph-aware one, so two edits of one node conflict; a graph deleted but not saved comes back as its old file.

## D-044 Preferences are a versioned JSON file that never fails to load

**Decision.** `PreferencesStore` (ProjectSystem, no Avalonia types) reads and writes `preferences.json` in the same per-user folder as `node-libraries.json`. It has a `schemaVersion` (1) and a list of migration steps like the graph format. Settings: recent projects (10, most recent first), autosave interval (0 = off, 10–3600 seconds), preview before generating, the netcoredbg path (used after `VSIDE_NETCOREDBG` and before the search), the Godot executable (D-047; added without a schema change, since a missing value means none), theme (dark, light, or system; D-046), and UI scale (75–200 %, applied with a layout transform to the whole window, which popups inherit through `Popup.InheritsTransform`). Loading never throws: a missing file gives the defaults; an invalid value falls back to its default and is reported in Output; a file that is not valid JSON is copied to `preferences.invalid.json` before the defaults are used. The file is parsed as a JSON object rather than deserialized, and saving writes the known settings into the object read from disk, so settings from a newer build (and its higher version) are kept. Tools → Preferences (Ctrl+,) edits them; File → Open Recent and the start screen list recent projects. **Why.** A broken settings file must not stop the IDE from starting, and downgrading must not erase settings a newer build added. Keeping the store in ProjectSystem makes it testable without a UI and usable by the CLI later. Trade-off: hand-written reading per setting instead of a serializer contract.

## D-043 An Explorer and editor tabs, VS Code style; the IDE manages its own files

**Decision.** The left panel's first tab is the **Explorer**: the solution with its projects, and the project folder as a tree (build output and tool folders such as `bin`, `obj`, and `.git` are hidden). The editor area shows one tab per open graph or file; graphs open on the canvas, every text file (handwritten C#, the `.csproj`, solutions, JSON, Markdown) opens in a text editor with find and replace, and the generated code of the open graph stays in the Code tab at the bottom. `ProjectFiles` (ProjectSystem) does all file management and refuses what the IDE or the generator owns: the `.vside` file, graphs (renamed and deleted in My Project, D-031), files with the ownership header, and the project folder; the `.csproj` can be edited but not renamed or deleted. Text that starts with the ownership header cannot be saved, so a handwritten file can never become one the generator would overwrite. Every path is checked to be inside the project folder. A `FileSystemWatcher` follows changes made by other tools: open files without unsaved changes here are reloaded, the tree and references refresh, and a changed `.csproj` whose packages need restoring offers `dotnet restore` (never runs it unasked, because restore evaluates the project's MSBuild files). The solution section lists the `.slnx` or `.sln` projects and adds a new project from a `dotnet new` template (class library, console, xUnit) next to this one, an existing project, or removes one, through the `dotnet` CLI (D-036). Tools → Open Folder in VS Code and the file tabs open VS Code, found through `VSIDE_VSCODE`, `PATH`, or its default install folders, started with an argument list. **Why.** Users expect the workflow of VS Code: one tree of everything in the folder, tabs that show what is being edited, and files beyond C#. Keeping the rules in ProjectSystem keeps them testable and UI-free, and one place decides what may be overwritten. Watching instead of locking lets VS Code and the IDE be used side by side. Trade-off: deleting a file or folder in the Explorer cannot be undone; a file changed on disk while it has unsaved changes here keeps the IDE's text, and saving overwrites the other change.

## D-042 MIT license, Velopack installers, unsigned for now

**Decision.** ScriptArt Code is released under the MIT license; packages declare it with `PackageLicenseExpression`. Phase 6 installers and updates use Velopack: a per-user install without admin rights on Windows, macOS and Linux packages, and updates (with deltas) read from GitHub Releases, applied only after the user agrees. Binaries are not code-signed yet. **Why.** MIT matches the main dependencies (Avalonia, AvaloniaEdit, Roslyn) and does not restrict node-library authors. Velopack is open source, built for .NET, and covers all three platforms and updates with one tool, where Inno Setup and MSIX are Windows-only and MSIX needs a trusted certificate even to sideload. No certificate is available. Trade-off: unsigned builds show SmartScreen (Windows) and Gatekeeper (macOS) warnings, which the install instructions explain; signing can be added to the packaging step later without changing the installer.

## D-041 Background compilation reads snapshots

**Decision.** Live compilation runs on a thread-pool thread against `VisualProject.Snapshot`: a read-only copy of the project whose graphs are deep copies (`GraphDocument.Clone`). The workspace keeps one copy per graph and reuses it until the graph's editor reports a change, so a snapshot after one edit copies one graph. A compile that a newer request superseded is discarded. Generation, preview, handwritten-code checks, and Go to Definition use snapshots too. The node library is copy-on-write, so registering a library while a compile runs is safe. **Why.** Compiling a 10,000-node graph takes about 75 ms, which stalled the UI thread on every edit. Copying is cheap (about 1 ms for 10,000 nodes) and gives each compile a consistent view without locks in the editing model. Trade-off: a result can describe a graph a few milliseconds old; the newest request always wins.

## D-040 The canvas indexes nodes and wires in a uniform grid

**Decision.** `SpatialIndex<T>` (NodeEditor) is a grid of 256-unit cells mapping to the items whose bounds touch them. The canvas keeps one index of node bounds and one of wire bounds (inflated for curvature), updated when layouts are rebuilt and per item during drags. Rendering, the marquee, and hit-testing query the visible or hit area; draw order comes from separate order maps. **Why.** Culling and hit-testing were linear in the graph size. A uniform grid is simple, has no rebalancing, and fits nodes of similar size; queries much larger than the occupied area visit only occupied cells. Trade-off: a wire spanning the whole graph is in many cells.

## D-039 Incremental compilation per graph

**Decision.** `GraphCompilationCache` keeps each graph's last result keyed by a SHA-256 of its serialized content and a fingerprint of everything else its code depends on: namespace, host class, node-library version, every graph's signature, and which graphs are async. Changing one graph's nodes recompiles that graph; changing a signature recompiles all. Graphs compile in parallel. Snapshot graphs, which never change, hash once per copy. Metadata references of referenced assemblies are cached by path, write time, and size. **Why.** Generating, previewing, and building compiled every graph each time. Keying on content rather than edit events makes the cache correct by construction: a stale result needs a hash collision. Trade-off: hashing is linear in the graph's size, which is far cheaper than compiling it.

## D-038 Node libraries are opt-in per user, pinned by hash, and isolated by load context

**Decision.** The types node definitions need (`NodeDefinition`, pins, `TypeRef`, the IR, lowering contexts) form `ScriptArt.NodeSdk`, a package third parties reference; contexts reach the compiler through an internal interface. A library is a .NET assembly with public `INodeProvider` classes. The IDE loads only libraries the user approved in Tools → Node Libraries, recorded per user (`%AppData%/ScriptArtCode/node-libraries.json`) with the file's SHA-256; a file whose hash changed is not loaded until approved again. The CLI loads only libraries named with `--node-library`. Projects cannot name libraries. A library loads from the bytes that were hashed, in its own `AssemblyLoadContext` that shares the SDK and graph model with the IDE. Faults (a missing file, a provider that throws, a type ID already in use) become messages, never crashes; a duplicate type ID keeps the existing node. **Why.** A library runs code with the user's permissions, so loading one is a trust decision that only the user can make, and opening a project from someone else must stay safe. Pinning the hash makes approval cover one file content, not whatever later appears at the path. Trade-off: a project that uses a library's nodes shows unknown-node errors on a machine without it, and removing a library takes effect after a restart because .NET cannot unload code still referenced by node definitions.

## D-037 The product is ScriptArt Code; the file format keeps its names

**Decision.** The IDE is named **ScriptArt Code**. Projects, assemblies, and namespaces are `ScriptArt.*` (`ScriptArt.App`, `ScriptArt.Compiler`, …), the IDE executable is `ScriptArtCode`, the solution is `ScriptArtCode.slnx`, and new generated files start with `// <auto-generated> Generated by ScriptArt Code.`. The project extension `.vside`, the CLI command `vside`, the environment variables `VSIDE_*`, node and pin type IDs, diagnostic codes (`VSG…`, `VSP…`), and the old `VisualStudioLikeIDE` ownership header are unchanged: a generated file with either header is owned by the generator. **Why.** The name should not suggest an affiliation with Visual Studio. The extension, IDs, and codes are part of the file format and of users' projects (AGENTS.md); changing them would break every existing project for no benefit. Recognizing the old header keeps generation working on projects created before the rename, and their files get the new header the next time they change. Trade-off: the extension and codes no longer match the product name.

## D-036 Solutions, packages, and project references go through the dotnet CLI

**Decision.** Project → Create Solution File runs `dotnet new sln --format slnx` and `dotnet sln add`; Add NuGet Package runs `dotnet add package` (id and version validated first); Add Project Reference runs `dotnet add reference` and, when the project has a solution, `dotnet sln add`; References removes either with `dotnet remove`. The IDE reads a project's packages and project references back from the `.csproj` (`ProjectReferences.Packages`, `Projects`) and turns a referenced project's public methods into nodes from its `bin/Debug/{framework}` assembly once it has been built. **Why.** The CLI is the supported way to change these files and keeps the user's formatting and MSBuild semantics (central package management, conditions) intact, which editing the XML ourselves would not. Commands run with argument lists, never a shell. The solution is optional because the `.csproj` builds alone. Trade-off: a command needs the SDK and, for packages, the network; a referenced project's nodes appear only after it builds.

## D-035 Debugging attaches netcoredbg to a program started by the IDE, and breakpoints are nodes

**Decision.** F5 builds, then starts `dotnet <assembly>` itself, with redirected input and output and a startup hook (`DOTNET_STARTUP_HOOKS`, a small assembly compiled with Roslyn once per hook version) that waits until a debugger attaches (at most 30 seconds). netcoredbg (MIT), found through `VSIDE_NETCOREDBG`, `PATH`, or `%LocalAppData%/ScriptArtCode/netcoredbg`, then attaches over the Debug Adapter Protocol: initialize, attach, wait for `initialized`, setBreakpoints, configurationDone. A breakpoint is a node (`NodeBreakpoint`, kept for the session); the source map (`DebugSourceMap`) turns it into the first line of the node's statement in its generated file, and a stop is mapped back to the node, which is selected and outlined. Breakpoints on nodes whose value is inlined into another statement are reported as not hit. **Why.** netcoredbg is the open-source debugger for .NET that speaks DAP, which Microsoft's vsdbg does not license for third-party IDEs. Launching through netcoredbg cannot forward standard input on Windows, and its server mode and suspended-runtime attach fail there; starting the process ourselves keeps the Output panel's input and output identical to Ctrl+F5, and the hook ensures no breakpoint is missed before attach. Mapping through the existing source map means a breakpoint survives regeneration as long as its node exists. Trade-off: netcoredbg is a separate download, no conditional breakpoints or watches yet, and stepping moves through generated C# lines rather than nodes.

## D-034 Go to Definition uses the graph for nodes and Roslyn for code

**Decision.** F12 with a node selected opens what the node uses (`GraphEditor.NavigationTargetOf`): a Call's function or method, a New node's constructor or type, a property node's type, Self's owner, a variable node's variable. F12 in the code view asks Roslyn (`CodeNavigator.FindDefinition`) for the declaration under the caret in a compilation of the generated and handwritten code, with unsaved text; a declaration in generated code is mapped through the source map to its graph and node, one in a handwritten file opens it at the line, and one in metadata is named in the status bar. **Why.** Nodes refer to graphs by id, so the graph model answers directly and without compiling; in code, Roslyn's semantic model is exact, including overloads and implicit constructors. Mapping generated declarations to graphs keeps users in the graph rather than in read-only code. Trade-off: no Find All References yet, and no decompiled source for .NET symbols.

## D-033 Generation is planned before it writes, and the plan can be previewed

**Decision.** `GeneratedFileWriter.Plan` computes the generated files that writing would add, modify, or delete, with their old and new text, and touches nothing; `Write` applies a plan. `VisualProject.PreviewGeneration` verifies the project with Roslyn and returns the plan; the IDE shows it (Build → Preview Changes Before Generating, on by default) as unified diffs from `TextDiff` (Myers' algorithm, capped edit distance), and `vside diff` prints them. **Why.** The same function decides what a preview shows and what a write changes, so the preview cannot drift from the real write. A git-style diff is familiar and readable for whole files. Ownership conflicts (VSP0001) are found while planning, so a preview already reports them. Trade-off: one extra click per generation while the preview is on; a very large change shows as a whole-file replacement after the edit-distance cap.

## D-032 Handwritten C# files are edited in the IDE and checked with the generated code

**Decision.** My Project lists the project's handwritten `.cs` files (any `.cs` outside `Generated/`, `bin/`, and `obj/` without the generator header). The Code tab edits one in place; its text is kept in memory with its own undo history until the project is saved, when `VisualProject.SaveSourceFile` writes it, refusing paths outside the project, non-`.cs` files, generated files, and text that starts with the generator header. While typing (debounced 600 ms), the project is verified with Roslyn with the unsaved text (`unsavedFiles`), and its diagnostics appear in Problems. Generation and Go to Definition use unsaved text too. **Why.** Handwritten code is the escape hatch for what graphs cannot express (CODE_GENERATION.md), and switching to another editor to write a helper breaks the flow. Verifying with unsaved text gives the same errors the build will. The save checks keep the ownership model: the IDE never writes a generated file as handwritten code, nor handwritten code that the generator would later claim. Trade-off: a basic editor (highlighting, no completion yet); a file changed on disk while open with unsaved changes keeps the IDE's text.

## D-031 Graphs are renamed and deleted in My Project, and node search understands everyday words

**Decision.** Graphs and variables are renamed in place in My Project (double-click, F2, or the right-click menu) and on the canvas by double-clicking a variable node or Function Entry; a Call node, or a New node that runs a constructor, opens that graph when double-clicked. Deleting a graph asks for confirmation, also deletes the methods and constructors a type owns, and is not undoable. Saving moves a renamed graph to `Graphs/{Owner.}{Name}.graph.json` when that name is a valid identifier and the file is free, and deletes files no graph uses any more. Node search (`NodeSearch`) ranks name prefixes, then word starts (directly, through a synonym table such as if→Branch or print→Print, or by initials), then mid-word matches, category, description, and one typo per word; built-in nodes come before .NET members among equal matches. **Why.** Projects with many functions and types need names that can change without leaving stale file names, and beginners search with words from other languages or with typos. **Alternatives.** Keeping first file names (confusing once projects grow); undoable graph deletion (would need project-level undo across editors).

## D-030 .NET constructors, properties, and generic methods are nodes named by documentation ID

**Decision.** `ExternalApi` also offers public constructors (`dotnet:M:T.#ctor(…)`), property getters (`dotnet:P:…`), and setters (`dotnet:set:P:…`). Instance members are offered on the framework value types `DateTime`, `TimeSpan`, `Stopwatch`, `Random`, and `StringBuilder` (`FrameworkValueTypes`), which variables, parameters, and properties can hold by their full name. A struct constructor and every property read are pure; a class constructor is a statement, and a struct property has no setter node. A generic method stores its type arguments in the node property `typeArguments`; an unknown type there is VSG0029. Optional parameters after the last one a graph can pass are left out. **Why.** Documentation IDs stay the one naming scheme for .NET members (D-021), and the `set:` prefix keeps a property's getter and setter distinct. Setting a property of a struct value would change a copy (CS1612), as for the project's structs (D-022). A short list of value types keeps the type lists usable; more can be added without a format change. Trade-off: a generic method is offered only when every type parameter can be chosen on the node.

## D-029 Waiting for an async call makes the method and its callers async

**Decision.** A .NET method returning `Task` or `Task<T>` is marked async; its node generates `await call` and outputs the task's result. A graph whose nodes wait, directly or through a call or a constructor that waits, generates an `async Task` (or `Task<T>`) method, and calls to it are awaited; an entry graph that waits generates `async Task Main()`. A constructor cannot wait. **Why.** Users of a node editor think in steps that finish one after another; awaiting every call keeps that model and avoids blocking with `.Result`. Computing which graphs are async from their nodes needs no flag to keep in sync and no schema change. Trade-off: no concurrent waiting (`Task.WhenAll`) or fire-and-forget calls yet, and making one deep function async changes the signatures of all its callers in generated code.

## D-028 Try catches a chosen exception type, and Rethrow is a node

**Decision.** The Try node's property `exception` picks the type its Catch output handles from a fixed list (`BuiltInNodes.CatchableExceptions`); its Message output is the caught exception's message. Throw Error's property `exception` picks the type it throws, from the types whose constructor takes only a message. A **Rethrow** node (`flow.rethrow`) generates `throw;` and is allowed only in a Catch block (VSG0031). **Why.** Catching everything hides bugs such as a null reference while handling a parse error; one chosen type per Try covers the common case without a list of catch clauses on one node. A fixed list keeps the choices valid without loading exception types. `throw;` keeps the original stack trace, which rethrowing the caught object would lose. Trade-off: one catch type per Try node; nest Try nodes to handle several.

## D-027 Classes and structs can be generic, and collections nest

**Decision.** A class or struct graph has `typeParameters` (schema version 8), usable as types inside the type, its methods, and its constructors. Elsewhere it is written with arguments (`Box<string>`), parsed by `TypeRef.FromName`; a generic type without its arguments is not a type. Type nodes and method calls of a generic type store their arguments in the node property `typeArguments`, and the palette offers them for each argument list the project uses, and inside the type for its own parameters. A property of a type parameter starts as `default!` in a class. Lists and dictionaries may contain any supported type, including other collections. **Why.** Generic containers are the main reason users write their own types after lists and dictionaries; reusing the per-node type naming of collections (D-024) needs no new mechanism. Offering only argument lists in use keeps the palette short. Trade-off: nothing is known about a type parameter, so its values can only be stored and passed on; no constraints, generic methods, or generic functions yet.

## D-026 Constructors are graphs owned by a class or struct

**Decision.** A constructor is a graph of kind `Constructor` with an `owner` (schema version 8), stored and generated like a method (`{Type}.{Name}`), with parameters and no return value. Inside it, Set nodes on Self assign the new object's or value's properties, also for a struct. A New node's property `constructor` picks the constructor and gives the node its parameters; a struct's New stays pure. A parameterless constructor is generated when a class has only constructors with parameters, or a struct has property initializers, so `new T()` keeps working. Two constructors of one type may not take the same parameter types. **Why.** Constructors reuse the parameter editing, Function Entry, and per-graph files of methods (D-025). The constructor's name exists only to name its graph and files, since C# names every constructor after its type. Keeping `new T()` means existing New nodes and variable initial values never break when a constructor is added. Trade-off: no constructor chaining (`: this(…)`) or base constructors.

## D-025 Methods are function graphs owned by a class or struct

**Decision.** A method is a function graph with an `owner` (the class or struct graph's id, schema version 7). It generates a public, non-static method in `{Type}.{Method}.g.cs`, and its type becomes `partial`. A pure **Self** node (`type.self`) is offered only in method graphs and generates `this`; it is resolved from the graph's owner, not a node property. The method's Call node (`function.call`, as for functions) gets a Target input and generates `target.Name(…)`. Calls to functions of the program class from a method name the class (`Program.Square(…)`), so functions are now `public static` instead of `private static`. Method names must be unique within their type and must not match a property or the type's name (VSG0027). A struct method can read its value but not change it, since structs have no Set nodes. **Why.** Reusing function graphs gives methods the existing parameter and return editing, Function Entry, Return Value, and call resolution by id, so renaming a method keeps its calls. One file per graph (D-017) continues to hold, and partial types let the type's file and its methods' files compile separately. A Self node rather than a Self output on Function Entry keeps wires short in a large method, as in other node editors, and needs no binding of `this` as a local. Naming files after the type lets two types each have a method called `Reset`. Trade-off: functions lose `private`; no overloads, static methods on types, or methods that change a struct in place; renaming a type leaves its methods' file names unchanged.

## D-024 Nodes of lists of project types and of dictionaries name their collection type and are offered when used

**Decision.** `TypeRef` gains an optional `KeyType`; `Dictionary<TKey, TValue>` stores the value type in `ElementType`. Keys are `int` or `string`; values, like list items, are a simple type or a class or struct of the project. Collections do not nest. Types keep being stored by C# name (`Dictionary<string, int>`, `List<Point>`), now parsed by `TypeRef.FromName`. List nodes of the simple types stay registered per element type (D-020). Nodes of a list of a class or struct (`list.add`, `flow.foreach`, …) and of a dictionary (`dictionary.set`, `dictionary.keys`, …) store the collection's C# name in the node property `collection` and are built per node, like type nodes. The palette and action menu offer them for each such type that a variable, parameter, return value, or property of the project uses. Keys and Values copy into a new list. Get Value has a Default input and generates `GetValueOrDefault(key, fallback)`. **Why.** Registering every combination would put dozens of nodes per class into the palette, and keys and values multiply that; offering the types in use keeps the palette short and still covers every wire a user can drag, because a collection value only exists where something has that type. Naming the type in the node keeps the format readable and needs no schema change; an older build reports an unknown node type instead of misreading it. `int` and `string` keys hash predictably; a `double` key is a known source of lookup bugs and a class key compares by reference. Copying keys lets a For Each change the dictionary without an exception, and the graph type system needs no key collection type. Trade-off: a collection type must be used somewhere before its nodes appear; renaming a class or struct breaks the nodes of its collections like its variables; a lookup never fails, so a missing key and a stored value equal to Default look alike; Contains Key tells them apart. A lookup that throws would stop the program on a typo, and a pin default would need a value for every class and struct.

## D-023 Nodes are added from a context-sensitive action menu; the project is browsed in My Project

**Decision.** Right-clicking empty space on the canvas (without dragging, which still pans) opens the action menu, which replaces the wire-only quick add. It lists nodes in collapsible categories, searchable, with a **Context Sensitive** toggle that is on by default. Context sensitivity comes from `GraphEditor.Actions(anchors, contextSensitive)`: it leaves out a second Entry or Function Entry node and, when there are anchor pins, every node that cannot connect to one of them. The anchors are the pin of a wire released on empty space, or the free pins of the one selected node (`GraphEditor.FreePins`), and `AddActionNode` wires the chosen node to the first anchor it fits, as one undo step. The left panel's **My Project** tab replaces the Graphs list and the Variables section of Details: collapsible sections per graph kind and for the open graph's variables, each with a **+** button. A selected variable is edited in Details and dragged onto the graph for a Get (Ctrl) or Set (Alt) node. The theme is unchanged. **Why.** Searching where the node will go is faster than the palette, and it is the workflow users of established node editors expect. Filtering and wiring live in the editor so they are testable without UI and use the same connection rules as dragging a wire. A turned-off filter still adds the node, just unconnected. Trade-off: right-click is no longer free for a node context menu, and the palette is one tab away instead of always visible.

## D-022 Classes and structs are graphs of properties; struct properties change by copying

**Decision.** A class or struct is its own graph file (`kind: Class` or `Struct`, schema version 6) holding `properties` with a name, type, and initial value, and no nodes. It generates an `internal sealed class` or `internal struct` with `{ get; set; }` properties in its own `.g.cs` file; an initializer is written only when the initial value differs from C#'s default, and a struct with initializers gets an empty parameterless constructor (CS8983). Types are named by their C# name in variables, parameters, return types, and properties, like lists (D-020), and resolved against the project's graphs (`TypeRef.FromName`); a project type is a `TypeRef` with an empty namespace. Type nodes store the type graph's id and the property's id and are resolved per node, like call nodes. New is a statement for a class and pure for a struct. A class property changes with a Set statement; a struct property with a pure With node (`value with { X = 3 }`) whose copy is stored with a variable's Set node. A type that contains itself through its properties is an error (VSG0030). **Why.** One graph per generated file keeps the project, the Graphs list, per-graph undo, and the generated layout uniform with functions (D-017), and leaves room for methods on types later. Naming types like the existing type names needs no new reference scheme in the file format. A class object has identity, so creating it at every use would make two uses see two objects; a struct has none. Assigning a property of a struct that came from a pure expression is CS1612 and silently changes a copy when it came from a parameter; With keeps value semantics visible in the graph. Every class property starts as a new object, so a class that contains itself would create objects forever, and a struct that contains itself has no finite size (CS0523). Trade-off: renaming a type does not update the variables, parameters, and properties that name it; a struct value with one property changed takes a With node and a Set node; no lists of types, nullable references, methods, or constructors yet.
